# Cosmos design workflow

For UI creation or redesign, start `plan_design` and keep its `workflowId` throughout. Follow the user's brief, project stack and existing conventions. Use HeroUI v3 as the default web component library. For an explicitly existing shadcn project preserve its stack. Use generic for standalone HTML or an incompatible project. Use SwiftUI for native iOS.

1. **Research.** Use the initial results from `plan_design` and refine with `search_patterns` when needed. Specify delivery platform separately from reference platform. Prioritize a named app or use the product category and interaction. Use `allowCrossPlatform` for deliberate cross-platform inspiration. Read the applicable guides with `read_design_skill`. Register provided PNG references in briefReferences, open every attachment with read_pattern, and use a concrete decision from each. Open the relevant catalogue images or flow and inspect returned pixels. If all results fail to open, tell the user which IDs failed. If there are no results, report the query. Candidate names from external research must be verified by the local catalogue.
2. **Direction.** For each observed region submit `id`, `region`, `visibleProperties`, `adaptation`, and `renderTarget` with a precise visible element, web selector or native accessibility identifier. Record separate decisions for distinct controls. Capture only observable effects such as transparency, edge reflection or blur. In inspiration mode preserve recognizable composition and control treatment with original identity. Only use faithful mode with confirmed ownership or permission, and add measured proportions, spacing, radii and visible states. The chosen reference must supply actual image bytes.
For `ios-agent-chat`, first inventory the canvas, back, agent, avatar, computer, messages, composer, auxiliary plus and send. Open idle and draft references and use each where appropriate. Capture measurements and icon shapes in notes. Use a native control or a platform-appropriate equivalent with original agent identity. Read every applicable guide before approval, submit a distinct application and verification in `skillPlan`, and supply distinct source or test evidence at review. Copy the approved audit map into the browser config. Compare the send control in the active draft state. See the [setup and audit guide](references/INSTALL.md).

For web projects using HeroUI, read the HeroUI and theSVG guides before design approval. Submit a distinct application and verification in skillPlan for every applicable skill. Add a measurable renderCheck to frontend-design and impeccable, using two distinct CSS properties or approved render targets that capture a visible design decision. Declare requested brand slugs in brandLogos or record why no third-party logos belong in the project. Retrieve each logo with read_brand_logo and write its exact SVG bytes. Use an original mark for the product itself.

3. **Build with actual files.** Call `get_design_assets`. It returns tokens generated by [UI/UX Pro Max](../ui-ux-pro-max/SKILL.md) and, where chosen, the [shadcn](../shadcn/SKILL.md) Button with its package provenance. Import the generated CSS or use the generated SwiftUI theme. For a shadcn project, use an existing registry Button or use the packaged source with the project's dependencies and Tailwind configuration. Keep existing project primitives and import paths. Apply [Web Accessibility](../web-accessibility/SKILL.md) to controls, keyboard and announcements. For native iOS use system controls, accessibility labels, Dynamic Type and safe-area layout. Register the entry, dependent component files, package.json and the CSS with record_design_implementation. On HeroUI projects, use the installed HeroUI components for every reusable interactive control. Do not simulate rendered provenance with hand-written data-slot attributes.
4. **Review the result.** Run a real browser or Apple Simulator. Use [Impeccable](../impeccable/SKILL.md) to find a visible defect in the actual captures returned by `open_design_render`. Improve it, re-register the source and reopen fresh captures. On web, apply [Web Design Guidelines](../web-design-guidelines/SKILL.md) to widths, overflow, and interaction. Start the local app and call run_design_audit with the [audit config](references/INSTALL.md). Exercise the primary keyboard interaction and assert the state it changes. Apply [Superpowers](../superpowers/SKILL.md) by reproducing issues before claiming fixes and rerunning verification. Enable uiKit in audit-web.cjs for HeroUI and declared brand slugs. Add a capture-ui step after opening a dialog or other dynamic state so the rendered primitives are verified. Pass designProbes for two pieces of visible content (product-specific focal point and copy) and one generated color token to the browser audit. For each required skill submit skillEvidence with skill, decision, path and an exact excerpt from registered source. For Superpowers cite the report from run_design_audit. Use the screenshots from that audit when opening the final web render. Pair each reference with a comparably framed screenshot in `open_design_render`. Inspect the paired image blocks at the same displayed width. Submit one `visualResults` entry per numbered decision with screenshot path, observed outcome and status. Reopen after fixing a failed comparison. Add measured evidence in faithful mode. Finish with `record_design_review` and the browser report path for web. Keep unavailable checks pending and report the exact limitation.

A complete UI task needs the built artifact. The final response should show or link to the rendered output, then report the reference IDs, the component and token evidence, the visual correction, executed tests and remaining checks. For a focused review or implementation on an existing design, the standalone `get_design_workflow` and `review_evidence` tools remain available.

## File access

The MCP can inspect generated project files only when it is configured with `COSMOS_PROJECT_ROOT`. If a screenshot or source inspection is unavailable, report that before claiming validation. When MCP tools are unavailable, the packaged [catalog](references/catalog.json) and [playbooks](references/skill-playbooks.json) can support a manual workflow.

For the bundled new-york-v4 Button, keep its visual styles on the component and put page layout on wrappers. Configure components.json and map the Tailwind semantic colors, border and radius before rendering. Set shadcnButtons in .cosmos/audit.json to a selector covering the actual user actions (e.g. "button" on an all-Button page). Run audit-web.cjs. Inspect each reported action and fix differences before final review.

## Full landing pages

When `plan_design` returns `landingResearch`, select a base by product and storytelling structure. Open the complete page with `read_pattern`, then use its `sectionId` values `hero`, `features` and `conversion` to inspect image crops. Convert each observation into an original design decision with `sectionId`, `productFeature` and a concrete visible `renderTarget`. The hero should answer what the product does and what to do next. The features should show the product in action. The close should address the next decision with evidence the user actually supplies. Use a practical workflow, real screenshots or an explicitly illustrative demo. Reference brands, claims and assets stay in the reference library.

Use `taskMode: edit` for a scoped revision and preserve unrequested sections. Skip the workflow for conceptual questions without a deliverable. For native iOS, use SwiftUI where appropriate and report native checks as unverified without Xcode and Simulator. For web motion, use the runnable `motionExample` from `get_design_workflow` with project-specific frames. Test reduced motion and sample timed states before claiming fluidity.
